================================================================
三个致命问题分析与建议
================================================================

问题 1：误识别严重（影子→楼梯，0.58 置信度就到达）
问题 2：没有全局方位感（landmark 之间的方向关系）
问题 3：给大模型的图片太模糊（看不清小字）


================================================================
问题 1：误识别 — 低置信度照样确认+到达
================================================================

【根因链】

GroundingDINO 检测到 "楼梯" 置信度 0.58
  → confirm_confidence_threshold = 0.50（默认值），0.58 > 0.50，通过
  → 连续 3 次（confirm_min_observations=3）都检测到"楼梯"
  → _try_confirm_candidate() 累积 3 次，坐标稳定 → evidence_level="confirmed"
  → can_complete=True
  → 到达判定：anchor_distance_m <= 1.4m → 触发到达
  → _advance_current_landmark() → 进入下一个 landmark

问题在于：DINO 是一个通用目标检测器，它不理解"楼梯"在语义上是什么样的。
地面的阴影、墙上的图案、甚至垃圾桶都可能被检测为 "stairs" 且置信度 > 0.50。
3 次连续误检就能 confirmed，太容易了。

【建议方案】

A. 提高 confirm_confidence_threshold（最简单）
   - 当前 0.50 → 建议 0.65 或 0.70
   - 0.58 的误检会被直接过滤掉
   - 代价：真正的低置信度正确检测也会被延迟确认
   - 风险低，立即可做

B. 加入 "一致性惩罚" 机制（更精细）
   - 如果同一个 label 的检测在短时间内 bbox 位置大幅跳动（比如影子随光照移动），
     说明不是稳定目标，应该 reset pending confirmed
   - 当前已有 anchor_jump 检查（confirm_max_anchor_jump_m=0.50），
     但影子可能在 0.5m 内反复跳动，刚好不触发 reset
   - 建议：加入 bbox 面积一致性检查 — 如果面积变化 > 50%，说明不是同一物体

C. 加入"视觉验证"层（最可靠但最贵）
   - 在 confirmed 之前，用 VLM 做一次验证：发送裁剪区域 + prompt
     "Is this image showing a staircase? Answer yes or no."
   - 只对 DINO 检测到但置信度 < 0.70 的情况触发
   - 代价：额外一次 API 调用，延迟 ~1-2s

D. 到达时增加视觉确认（推荐结合 A）
   - 当前到达判定只看距离，不看当前帧是否还能看到目标
   - 建议：到达条件增加 "当前帧可见 或 最近 N 帧内见过"
   - 这样即使之前的 confirmed 是误检，到达时如果看不到也不会触发

E. 针对特定 landmark 类型设置不同阈值
   - "楼梯" 这类容易和阴影混淆的目标，阈值设更高（0.70）
   - "轮椅" 这类形状独特的目标，阈值可以低一些（0.55）
   - 实现方式：在 config 中加 landmark_confidence_overrides 字典

【推荐组合】A + D（提高阈值 + 到达时视觉确认）


================================================================
问题 2：没有全局方位感
================================================================

【当前状态】

VLM 收到的信息：
  - 当前目标："楼梯"
  - Route steps: [{"landmark": "轮椅", "directive": "向前走"}, {"landmark": "楼梯", "directive": "向左前进"}]
  - Directional clauses: ["向前走", "向右绕过", "向左前进", "直走"]
  - Route context: "completed: 轮椅; current: 楼梯"（仅此而已）

问题：VLM 不知道"楼梯"相对于"轮椅"在什么方向。
它只知道当前目标是"楼梯"，但不知道应该往哪个大致方向找。

例如：指令说"找到轮椅，然后向右绕过轮椅之后向左前进，再直走找到楼梯"
- 轮椅在前方 → 右绕 → 左转 → 直走 → 楼梯
- 如果轮椅已确认在 (3.0, 4.0)，那么楼梯大致在 (3.0 + delta_x, 4.0 + delta_y)
- 但 VLM 完全不知道这个全局关系

【建议方案】

A. 在 route_context_text 中加入已完成 landmark 的世界坐标（最简单）
   - "completed: 轮椅 at (3.0, 4.0); current: 楼梯; direction from previous: forward-left"
   - VLM 可以据此推断搜索方向
   - 实现：修改 _build_route_context_text()，加入 confirmed anchor 坐标

B. 构建 landmark 方向图（更系统）
   - 解析指令中的方向链：向前走→轮椅 → 右绕→轮椅 → 左转前进 → 直走→楼梯
   - 推算每个 landmark 相对于前一个的大概方向
   - 存为 InstructionContext.landmark_direction_hints
   - 在 prompt 中提供："Based on instruction analysis: stairs should be roughly FORWARD-LEFT relative to wheelchair location"

C. 用已完成 landmark 的历史轨迹推算（最精确）
   - 记录机器人从 start → landmark1 → landmark2 的轨迹
   - 当前位置相对于 landmark1 的方位 + 指令中的转向信息 → 推算 landmark2 的大概方向
   - 作为 VLM prompt 的 "expected_direction" 字段

D. 在 occupancy map 上标记全局方向提示（视觉化）
   - 在 debug 图像上，从当前位置画一条虚线指向下一个 landmark 的推算方向
   - VLM 看图就能知道大致方向
   - 代价：需要在图像上叠加标注

【推荐组合】A + B（坐标 + 方向推算，成本最低效果最好）

【具体实现思路】

在 vln_policy.py 的 _build_route_context_text() 中：
  已完成 landmark 的 confirmed anchor 坐标 → 计算相对方位
  当前目标的推算方向（基于指令中的方向链）

示例 prompt 增强：
  "Route context: completed landmarks: wheelchair at (3.0, 4.0).
   Instruction analysis: after wheelchair, turn right then go left then straight → stairs expected roughly FORWARD-LEFT from current heading.
   Current robot heading: 45°. Expected stairs direction: approximately -30° to +30° relative to current heading."


================================================================
问题 3：给大模型的图片太模糊
================================================================

【当前配置】

camera.width = 640, camera.height = 480
llm.upload_max_edge_px = 512  ← 最大边 512px
llm.camera_image_detail = "high"

上传流程：
  640x480 原图 → 最大边 512px → 缩放到 512x384 → PNG 压缩 → base64 → API

问题：
1. 512px 太小。640x480 本身就不大，再缩到 512x384，细节严重丢失
2. "high" detail 在 512px 下效果有限 — detail 参数控制的是 API 端的处理方式，
   但如果输入图片本身就糊，high detail 也救不回来
3. 小字（比如标识牌上的文字、远处的目标）在 512px 下基本不可读

【建议方案】

A. 提高 upload_max_edge_px（最直接）
   - 512 → 1024 或 1280
   - 代价：token 消耗增加（约 4x），API 延迟略增
   - Qwen3-VL 支持高分辨率输入，1024px 是合理范围
   - 建议先试 1024，观察 token 用量和延迟

B. 提高相机原始分辨率
   - camera.width = 640 → 1280, camera.height = 480 → 720
   - 代价：Isaac Sim 渲染负载增加，GPU 显存占用增加
   - 但这样原图就有足够细节，缩放到 1024 仍然清晰
   - 注意：可能加剧你之前遇到的 GPU OOM 问题

C. 分辨率自适应（精细方案）
   - 近距离目标（depth < 2m）：用高分辨率 crop + 高 upload_max_edge
   - 远距离目标（depth > 4m）：用全图 + 标准 upload_max_edge
   - 实现：在 _prepare_image_upload() 中根据目标距离选择策略

D. 裁剪感兴趣区域（ROI）
   - 如果 DINO 已经给出了目标 bbox，裁剪 bbox 区域（放大 1.5x margin）
   - 单独发送 ROI 给 VLM 做细节判断
   - 全图用于全局导航，ROI 用于目标确认
   - 代价：可能需要两次 VLM 调用，或在 prompt 中说明 ROI 位置

E. 使用 JPEG 代替 PNG（压缩效率）
   - 当前用 PNG optimize=True，无损压缩
   - JPEG quality=85 视觉上几乎无损，但文件小很多
   - 这样同样的文件大小可以传更高分辨率的图
   - 改动小：_prepare_image_upload() 中 format="JPEG", quality=85

【推荐组合】A（提高 upload_max_edge 到 1024）+ E（JPEG 代替 PNG）

【注意】
提高 upload_max_edge 会增加 token 消耗。Qwen3-VL-30B 的 token 计费：
  - 512x384 ≈ 约 800-1200 image tokens
  - 1024x768 ≈ 约 2500-3500 image tokens
  - 差异约 3x，但在 SiliconFlow 上费用应该可控

建议先在 configs/default.yaml 中改为：
  llm:
    upload_max_edge_px: 1024
测试一下效果和延迟，再决定是否继续提高。


================================================================
优先级总结
================================================================

问题 1（误识别）：
  P0: 提高 confirm_confidence_threshold 到 0.65-0.70
  P1: 到达时增加"当前帧可见"检查
  P2: bbox 面积一致性检查

问题 2（全局方位感）：
  P0: 在 route_context 中加入已完成 landmark 的世界坐标
  P1: 构建指令方向链，推算下一个 landmark 的预期方向
  P2: 在 occupancy map 图像上叠加方向提示

问题 3（图片模糊）：
  P0: upload_max_edge_px 512 → 1024
  P1: PNG → JPEG (quality=85)
  P2: 相机分辨率 640x480 → 1280x720（需评估 GPU 影响）
  P3: ROI 裁剪方案


================================================================
三个问题的相互关系
================================================================

问题 1 和问题 3 是关联的：
  图片模糊 → DINO 看不清 → 低置信度误检 → 但阈值太低仍然通过 → 误到达
  提高图片分辨率 + 提高确认阈值，双管齐下效果最好

问题 2 和问题 3 也是关联的：
  图片模糊 → VLM 看不清远处标识 → 方向判断失误
  如果有了全局方位提示，即使看不清，VLM 也能根据方向推断
  → 问题 2 的方案 B 可以部分缓解问题 3
